HOW AI BENCHMARKS ARE ACTUALLY BUILT, AND WHERE SUPERCARTO'S BENCHMARK STANDS
Prepared October 7, 2026

PART A. THE SOP AI BENCHMARKS FOLLOW

Note first: there is no single official SOP. What exists is a set of published checklists, plus the practice visible in well-regarded benchmarks. The steps below are the common core of these sources. Each step lists where it comes from.

Sources used most
- BetterBench (Stanford, NeurIPS 2024): 46 criteria across design, implementation, documentation, maintenance. https://betterbench.stanford.edu/methodology.html and https://betterbench.stanford.edu/checklist.html and https://arxiv.org/abs/2411.12990
- ABC, Agentic Benchmark Checklist (NeurIPS 2025): task validity, outcome validity, reporting. https://arxiv.org/abs/2507.02825 and https://uiuc-kang-lab.github.io/agentic-benchmarks/
- LongMemEval (ICLR 2025): https://arxiv.org/abs/2410.10813
- MemoryBench (ICML 2026): https://arxiv.org/abs/2510.17281 and https://github.com/THUIR/MemoryBench
- MobilityBench (route-planning agents, 2026): https://arxiv.org/html/2602.22638v1
- MapEval (ICML 2025): https://arxiv.org/abs/2501.00316
- Datasheets for Datasets: https://arxiv.org/abs/1803.09010
- Croissant dataset metadata: https://docs.mlcommons.org/croissant/
- Reproducible evaluation lessons (lm-eval-harness authors): https://arxiv.org/abs/2405.14782v2

STEP 1. Define the capability being tested
What is done: write down the exact capability, why a task measures it, who uses the score, and how the score should and should not be interpreted.
Source: BetterBench design criteria (definition of tested capability, how it translates to the task, real-world usefulness, use cases and personas, how scores should and should not be interpreted). ABC R.5 and R.6 ask for construct validity.
Example: LongMemEval defines five memory abilities (information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention).

STEP 2. Build a task taxonomy
What is done: split the capability into named categories, each with a rationale.
Source: BetterBench "documentation of test task categories and rationale". MapEval uses place info, nearby, routing, trip, unanswerable. MobilityBench builds its taxonomy from intent classification of real queries.

STEP 3. Construct the dataset
What is done: choose sources, collect or generate instances, annotate, filter, record every step.
- Real or realistic source material. MobilityBench uses 100,000 episodes from anonymized real navigation queries. MapEval uses 700 expert-written questions built from Google Maps data.
- Human or expert involvement. LongMemEval has 500 manually created questions. BetterBench scores "involvement of domain experts".
- Controlled generation. LongMemEval builds a length-configurable chat history per question and ships two standard sizes so results stay comparable.
- Filtering. MobilityBench drops episodes whose answers cannot be reliably verified by tool execution.
- Document it: data sources, preprocessing, annotation process (BetterBench), and a datasheet (Gebru et al.).

STEP 4. Fix the ground truth and freeze it
What is done: ground truth is verified, not assumed, and does not change between runs.
Source: ABC T.7 and T.8 (verify ground truth and task setup), T.9 (provide an automatic oracle solver to prove the task setup is correct), T.10 (inspect outliers in pilot runs: agents failing easy tasks suggests impossible tasks, agents passing only hard ones suggests shortcuts).
Example: MobilityBench records tool responses during ground-truth creation and replays them from a cache, so live traffic or map changes cannot alter results. MapEval-API also built a controlled environment for the same reason.

STEP 5. Isolate the test environment
What is done: the agent cannot see answers, and no state leaks between tasks.
Source: ABC T.4 (clean all legacy state before each task), T.5 (fully isolate the agent from ground truth). Their example: KernelBench left ground-truth answers readable in GPU memory. ABC T.1 to T.3: pin tool versions, handle API rate limits, and stop the run if the API breaks rather than scoring failures.

STEP 6. Design the scoring so success means the capability
What is done: the pass condition is equivalent to real success.
Source: ABC outcome validity checks. Substring and whole-string matching must handle equivalent answers, redundant words and negation. Known failures they found: SWE-Lancer scoring 100 percent without resolving tasks, WebArena string matching overestimating by 5.2 percent, tau-bench letting a trivial agent pass 38 percent of tasks.
BetterBench: informed choice of metric, a floor and ceiling for the metric, validated automatic evaluation, sensitivity to input changes.
MobilityBench goes further and scores several dimensions (outcome, instruction understanding, planning, tool use, efficiency), not just end success.

STEP 7. Set baselines
What is done: measure the floor and ceiling before measuring systems.
Source: BetterBench (random performance level, human performance level). ABC R.12 and R.13 (baseline comparisons, including trivial agents). For a system that adds a tool or framework, the natural baseline is the same model with no tool, and with raw data instead of the framework.
MemoryBench compares memory systems against plain baselines, and LongMemEval compares memory designs against full-context reading.

STEP 8. Write the run protocol
What is done: one fixed procedure for running a model on the benchmark.
Source: BetterBench (evaluation code available, script to replicate results, requirements file, quick-start, supports API and local models). Reproducibility lessons paper: share exact prompts, record model and library versions, report settings that were really used.
Fixed items to record per run: model id and version, date, code commit, prompt, tool versions, decoding settings, number of repeats.

STEP 9. Run enough repeats and report uncertainty
What is done: more than one run, with an error bar.
Source: BetterBench (statistical significance of results for at least one model). ABC R.10. The ABC paper also suggests sampling with uncertainty estimates when ground truth is noisy.

STEP 10. Report results honestly
What is done: score tables plus limitations.
Source: ABC R.7 to R.11 (mitigations for known flaws, evidence of their impact, interpretation guidelines). BetterBench (documentation of limitations, normative assumptions, and differences from related benchmarks).

STEP 11. Release
What is done: publish data, harness and docs so others can rerun.
Source: ABC R.1 and R.2 (open-source dataset and harness), R.3 and R.4 (measures against contamination). BetterBench: license, persistent identifier, standard metadata (Croissant), unique identifiers or encryption of test instances to limit training on the test set, release requirements, code documentation.

STEP 12. Maintain
What is done: versioning, bug fixes, build status, contact route.
Source: BetterBench maintenance criteria and lifecycle model (https://betterbench.stanford.edu/methodology.html).

PART B. IS THE "NO PUBLIC BENCHMARK OR DATASET EXISTS" CLAIM TRUE?

Short answer: not as stated. Public benchmarks and datasets for LLMs doing map, route and geospatial tasks exist. What I could not find is one that compares map-data frameworks or representations for LLM agents (compact graph vs raw GeoJSON vs tool APIs), measuring accuracy together with context cost. That narrower claim looks defensible, but it is my search result, not proof. I searched the web only; I did not search Google Scholar or Hugging Face exhaustively.

Existing work that overlaps (honest list)
1. MapEval. 700 expert-made questions on places, nearby, routing and trips. Has a MapEval-API track where agents call map APIs. Evaluated 30 models. Evaluates models, not competing map-data frameworks. https://arxiv.org/abs/2501.00316 and https://mapeval.github.io/
2. MobilityBench. 100,000 route-planning episodes from real Amap queries, deterministic API-replay sandbox, multi-dimension scoring. The closest to your design in method (replay for reproducibility). Tests agents on one vendor's API set. https://arxiv.org/html/2602.22638v1
3. Map2Route. Human-curated compositional language-grounded route planning over semantic maps. https://arxiv.org/abs/2609.17910
4. GeoAgentBench (GABench). 117 GIS tools, 53 spatial analysis tasks, dynamic sandbox for tool-augmented GIS agents. GIS analysis, not navigation or map-to-LLM representation. https://arxiv.org/html/2604.13888 and https://github.com/GeoX-Lab/GABench
5. GeoLLM-Engine. Environment for geospatial copilots (earth observation). https://arxiv.org/html/2404.15500
6. GeoBenchLLM. 12 datasets, 8 geo task types. https://huggingface.co/datasets/rfr2003/GeoBenchLLM
7. MapQA (open-domain geospatial QA on map data). https://arxiv.org/html/2503.07871v1
8. Map image benchmarks for vision models: MapBench (https://arxiv.org/html/2503.14607), MapVerse (https://openaccess.thecvf.com/content/WACV2026/papers/Bhat_MapVerse_A_Benchmark_for_Geospatial_Question_Answering_on_Diverse_Real-World_WACV_2026_paper.pdf), FRIEDA (https://github.com/knowledge-computing/FRIEDA), transit map reading (https://arxiv.org/html/2505.18675v2). These are about reading map images, a different input.
9. Path planning by LLMs on real roads. https://arxiv.org/html/2411.17912v2
10. Closest on the "how do you show a graph to an LLM" question: a controlled urban-graph QA benchmark across three cities comparing seven graph-language interfaces (compression, memory, retrieval, execution, others). Graph tool access scored 87.4 percent, the best of those reported. Research benchmark on graph QA, not a framework comparison with MCP tools. https://isprs-annals.copernicus.org/articles/XII-4-W2-2026/155/2026/isprs-annals-XII-4-W2-2026-155-2026.pdf
11. Generic MCP tool-use benchmarks: MCP-Atlas (https://github.com/scaleapi/mcp-atlas) and MCP-Universe (https://arxiv.org/pdf/2508.14704v1.pdf). Not map-specific.

What is and is not covered
Covered by others: LLM map QA, route planning with APIs, GIS tool use, map image reading, graph QA.
Not found: a public benchmark where the variable under test is the map data system or framework itself (supercarto vs raw OSM/GeoJSON vs a vendor API), across spatial task types such as routing, indoor floors, weather, traffic and terrain, with context-token cost as a reported axis. Also not found: a public dataset of paired (map area, compact graph, verified answers) for that purpose.

Safe wording for the README or paper
Do say: "Existing benchmarks evaluate models on map and route tasks (MapEval, MobilityBench, GeoAgentBench). We found no public benchmark that compares map-data frameworks for LLM agents on accuracy and context cost, so we built one."
Do not say: "no benchmark or dataset exists for spatial mapping." That is false and a reviewer will find MapEval in minutes.
Also cite these as related work and explain how yours differs (BetterBench asks for "explanation of differences to related benchmarks").

PART C. MAPPING EACH STEP TO THE CURRENT SUPERCARTO BENCH
Status comes from the earlier audit of commit 4723869 (October 7, 2026, 9:42 PM IST). No fixes have been made. The audit read the code and did not run it.

1. Define capability (Step 1): Partly. Idea is clear (does the framework help an LLM answer map questions). Needs a written definition, intended users, and how to read scores. Not in the repo as a document.
2. Task taxonomy (Step 2): Partly. Tasks exist (turn-by-turn, connectivity and others) but there is no written rationale per category.
3. Dataset construction (Step 3): Weak. Truth is built live from map data, with no frozen, versioned dataset and no documented sources, preprocessing or datasheet. This is also what you want to release as the dataset.
4. Ground truth frozen and verified (Step 4): Fails. Audit found: turn-by-turn prompt asks for 200m but truth routes to the area radius (400 to 2000m); connectivity truth is compiled at budget 4000, not the budget shown to the model; raw GeoJSON is graded against a supercarto-compiled graph. Map truth is live, so it can change between runs. No oracle solver check. Fix: freeze answers, add a check that a perfect solver scores 100 percent (ABC T.9).
5. Isolation (Step 5): Fails. The agent runs inside the repo folder where tasks and answers sit, so the none arm cannot be trusted. The code does void detected tool events, which is good. Fix: fresh empty folder and isolated config, then test that it really blocks every tool-event shape.
6. Scoring validity (Step 6): Fails. Scorer checks street-name substrings, not directions or order, so right answers can score wrong and wrong answers can score right (ABC outcome validity).
7. Baselines (Step 7): Partly. A no-framework arm and a raw arm exist in design. Not trustworthy until Steps 4 to 6 are fixed. No random or trivial-agent floor.
8. Run protocol (Step 8): Weak. Docs claim temperature 0 and seeds, but OpenCode never receives them. Docs promise provider tokenizers and paid models, but tokens are chars/4 estimates. The model-call cap does nothing (a default run can make about 168 calls). Reports do not save commit, OpenCode version or frozen answers. Resume can mix old and new runs after code changes.
9. Repeats and uncertainty (Step 9): Weak. Default is one repeat, no error bars. Plan: 3 repeats on a small run.
10. Honest reporting (Step 10): Fails today. README shows 88 / 62 / 9 percent and a context-cost table with no committed raw results behind them (.bench/ is gitignored). Remove them or label as "example format" until a real run backs them.
11. Release (Step 11): Not started. Needs license note for data, dataset metadata, raw outputs committed, and a quick-start.
12. Maintain (Step 12): Not started. Version the dataset and keep a changelog.

Suggested order of work, if you approve it
1. Stop the unbacked claims (Step 10 item above).
2. Isolation fix and test (Step 5).
3. Freeze ground truth and fix task and scoring mismatches (Steps 4 and 6).
4. Remove fake temperature and seed claims, make the call cap real, record run metadata, make resume safe (Step 8).
5. One small free-model run: one model, three arms, three repeats, raw outputs committed (Step 9).
6. Write the datasheet and related-work section using Part B (Steps 1, 3, 10, 11).
No work has started. Free models only for any run.
