Interfaces

HTTP API

The maplet, screen, transit and route endpoints, with parameters and examples.

Boot the API locally:

supercarto serve --port 8787

It serves GET /maplet, GET /scr, GET /transit and GET /transit-route, each answering YAML (format=yaml) or JSON. GET /health reports the server’s cache health.

GET /maplet

latquerynumberrequired
Latitude in [-90, 90].
lonquerynumberrequired
Longitude in [-180, 180].
radiusMqueryinteger
Default: 300
Radius in metres, clamped to the machine’s limit.
budgetqueryinteger
Default: 1024
Token budget for the emitted YAML.
layersquerystring
Comma-separated layer filter.
formatquerystring
Default: json
yaml returns the agent-ready document directly.

Errors are honest too

A deployment with no GTFS feed configured answers 404 with “no GTFS feed configured for this deployment” rather than a transcript-shaped “no service” — the refusal names the action (set SUPERCARTO_GTFS or pass ?feed=) that makes the tool exist.

GET /transit

Same parameter style: lat, lon, radiusM, budget, at (the instant to evaluate), and format. The per-deployment feed comes from SUPERCARTO_GTFS; a specific request can name its own feed with ?feed=<dir or zip>, and the operator’s SUPERCARTO_GTFS_RT follows feed overrides, so a feed override never silently drops live data.

GET /transit-route

Adds fromLat, fromLon, toLat, toLon, and maxWalkM. The answer is the certified ride plan.

curl 'localhost:8787/maplet?lat=35.6833&lon=139.762&radiusM=400&budget=1500&format=yaml'
map:
  center: "35.6833, 139.762"
  radius: 400m
nodes:
  n186: {type: transit, name: 新橋駅(3), tags: [subway_entrance]}
edges:
  n1->n2: {dist: 120m, dir: east, path: road}
omitted:
  - {layer: feature, count: 1754}
